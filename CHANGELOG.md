# Changelog

## [Unreleased]

### Added

- **Named images (CC-fancy-0039).** The host registers images with the writer by name, `toBytes($doc, ['images' => ['logo' => <PNG/JPEG bytes or data URL>, 'seal' => ['data' => ..., 'widthPx' => 150, 'heightPx' => 50, 'alt' => 'Acme Ltd']]])`, and the model places one with `{"type": "image", "src": "image:logo"}`: in the body, a footnote, or a header or footer that holds `blocks`, so a letterhead carries the logo. Resolved at write time to exactly what the same image as a data URL writes. A block's own `widthPx` / `heightPx` / `alt` win over the registered ones. `write()` and `layout()` take the same option.
- `imageLimits` (`maxBytes` 5 MiB, `maxWidthPx` and `maxHeightPx` 4096, `maxImages` 32 by default; positive integers): every image is checked as it is registered, its type from its leading bytes, its size before it is decoded, its pixel size from its header. A refused one throws the new `LastWord\Exceptions\ImageRefused`, whose `reason` is a stable code: `image_option_invalid`, `image_name_invalid`, `image_data_invalid`, `image_type_unsupported`, `image_too_large`, `image_dimensions_unreadable`, `image_dimensions_too_large`, `image_count_exceeded`, `image_limits_invalid`.
- `Agent::guide($options)` and `Agent::jsonSchema($options)` take `images` too: the guide gains a section listing each name with its type, pixel size, placed size and alt, and the image block's `src` pattern takes exactly those names. **Without images both are byte-for-byte what they were**, so the guide's shared hash and the `doc-model/shared` conformance rows do not move.
- `Agent::validate($doc, $options)` and `Agent::validateAndRepair($doc, $options)` take `images`: a name nobody registered is an error with `code: "image_unknown"`, and `toBytes()` throws `SchemaException` carrying it.
- Dev: `tests/fixtures/named-images.json`, shared byte for byte with the Node package (both pin its sha256): the images, four documents (body, letterhead with the logo, name and contact block in the header and a page-numbered footer, first-page letterhead, footnote and footer), the guide and schema text, every refusal and its code, and the sha256 of every part each document writes. Regenerated by `tests/Support/build-named-images.php`. `NamedImagesTest` also opens the letterhead in LibreOffice where it is installed.

### Changed

- **An image `src` starting `image:` is now a named image.** Without the `images` option such a src was refused as "not a PNG or JPEG data URL" and `validateAndRepair()` dropped the image; it is now an `image_unknown` error naming the registered images (or saying there are none), and repair keeps the block so the model can correct the name. **Consumer action:** none, unless you match validation messages for such a src; branch on `code` instead.

## [0.20.0] - 2026-11-04

**What you must do: only if you read a `.docx` with more than one section, or wrote a page key straight on a break.** Otherwise a document writes exactly what it did, byte for byte, and reads what it did.

### Added

- **Mixed page orientation in `.docx`.** A `pageBreak` carrying `page` starts a new Word section: the vocabulary `fine-print` already has, with no new element and no `sections` key. `margins` merge side by side; every other key is replaced whole; `firstHeader` / `firstFooter` are never inherited; `page.background` on a break and `page` on a nested break are refused; `{"type": "pageBreak", "page": {}}` is valid. Each text width gets its own header and footer parts, because one-line bands hard-code tab stops and table bands a grid; the first stretch keeps `header1`-`header3` and `footer1`-`footer3`, so a document without such a break writes the same bytes. Later parts number from 5.
- `Schema::stretches()` and `Schema::isPageObject()`: the same reading of a document as `fine-print`'s.
- `describe()` says `Stretches: 3 (portrait, landscape, portrait)` for such a document.
- `layout()` lays each stretch out at its own page and text width. Each `pageList` entry gains `section`, `width` and `height`; `page` stays the first page's.

### Changed

- **BREAKING: `read()` of a multi-section file.** Top-level `page` is now the FIRST section (it was the last), and each later section is a `pageBreak` holding only what differs, instead of the blocks running together. **Consumer action:** if you relied on `page` being the last section, read it from the last break's `page`, or merge them with `Schema::stretches()`. A file with one section reads as before.
- **BREAKING: `pageBreak.page` is no longer refused**, and `validateAndRepair()` keeps it: a document that was `ok: false` for that reason alone is now written. **Consumer action:** none, unless you relied on the refusal; if you sent such documents to `fine-print` for that reason, you can now write them here.
- `validateAndRepair()` moves a page key written straight on a break into `page`, with a note, as `fine-print` does; a background goes, also with a note, and a `page` on a nested break or one that is not an object is removed with a note. Those were `ok: false` before. `validate()` still refuses all of them by name, and a top-level `sections`.
- `read()` reports more through `unrepresented`, kind `layout-not-preserved`: `w:cols` above 1, a page-number restart and a paper size other than letter, legal or A4 are dropped, as they always were, and now say so, in a one-section file too. `oddPage` / `evenPage` starts read as a break and a report; `continuous` with the same size and orientation reads as no break and a report. **Consumer action:** none; if you treat any report as a failure, a custom paper size now is one.
- `{section}` caches its section's number rather than 1 in each later section's part. Word computes it; LibreOffice shows the cached one.

### Security

- Every XML part of a file, read or carried, now goes through one gate
  (`Archive\PartXml`), which refuses a part declaring a DOCTYPE. A refused part reads as
  an unparsable one: `word/document.xml` throws as it does when malformed, an ODT part
  throws as it did, a template part throws `TemplateException`, and any other part reads
  as absent. **Consumer action:** none; no Word or ODF file has a DOCTYPE. A header part
  with one used to read as a one-line band and now reads as no header.
- A package whose `[Content_Types].xml` declares a DOCTYPE is refused whole, with
  `OfficeTemplateRefused` reason `refused_declaration`, as a macro-enabled template is.
  **Consumer action:** none, unless you branch on `reason`. A merely malformed one reads
  as it did.

### Removed

- The refusal `pageBreak.page is not implemented in last-word yet`, and the `/page` report counting flattened section breaks. **Consumer action:** none. `/page` still reports what the first section drops.

### Fixed

- The test suite no longer fills the temp folder: `tempnam(...) . '.docx'` left its placeholder behind, about 1,300 files a run, and each LibreOffice oracle case left its profile. Tests take paths from `lwTemp()` and `lwTempDir()`, deleted at shutdown. Nothing about the package changes.

## [0.19.0] - 2026-11-03

**What you must do: only if you write a table cell with a `colSpan` above 1000.**
That is far past what Word itself makes (Microsoft documents 63 columns). `validate()`
now refuses it and ``validateAndRepair()`` clamps it to 1000 with a note and keeps the text. Every other
document writes exactly what it did, byte for byte.

### Added

- `Schema::MAX_COL_SPAN` (1000), also the `maximum` of `colSpan` in `jsonSchema()`.

### Changed

- **BREAKING: `colSpan` above 1000 is a validation error**
  (`colSpan must be at most 1000`). **Consumer action:** none unless you write such
  a span; `validateAndRepair()` clamps it. `rowSpan` has no ceiling: nothing costs
  more than the rows that exist.

### Fixed

- `Layout\TableGrid` no longer spends memory on each slot a span covers, so a
  table's layout cost does not grow with its spans. Placement is unchanged.
- `toPortable()` / `extract()` refuse a table over the `columns` limit before
  padding its short rows, not after. The refusal is the same
  `content_too_many_columns`; on a table that was also malformed it now reports
  this code rather than `content_invalid`.

### Security

- A table cell's column span had no upper limit, so a very small document could
  cost memory out of proportion to its size in `toBytes()`, `write()`, `layout()`,
  `toPortable()` and `extract()`. The validator, the repairer, the writer, the
  layout and the `.docx` reader now all hold it to 1000. Reading a `.docx` clamps
  and keeps the text; it never refuses for this. **Consumer action:** upgrade,
  especially if you accept documents or `.docx` files from users or agents.

## [0.18.0] - 2026-11-03

**What you must do: only if your documents carry `pageBreak.orientation`,
`pageBreak.margins` (or any page key straight on a break) or a top-level
`sections`.** Those were silently ignored and are now errors. Remove them, or
use `pageBreak.page`, which `fine-print` honours for PDFs today and `last-word`
will honour in a later release. Until then `last-word` refuses it. A document
without those keys writes exactly what 0.17.0 wrote, byte for byte.

### Changed

- **BREAKING: `pageBreak.orientation`, `pageBreak.margins`, `.size`, `.header`,
  `.footer`, `.firstHeader`, `.firstFooter`, `.evenHeader`, `.evenFooter`,
  `.background`, `.border` and a top-level `sections` were silently ignored and
  are now errors.** The document came out all portrait and looked fine, with no
  word that the request had been lost. The message names the form to use:
  `a pageBreak has no orientation key; use pageBreak.page`, and
  `there is no sections key; use pageBreak.page`. Every other extra key on a break
  stays lenient: agents decorate. **Consumer action:** remove those keys, or for
  mixed pages use `pageBreak.page`, which is not honoured here until a later
  release (below).

### Added

- **`pageBreak.page` is refused until it can be written** (mixed page orientation,
  stage 1): `pageBreak.page is not implemented in last-word yet; remove page to
  keep one page setup, or write this document as a PDF with fine-print`. It is part
  of a vocabulary `fine-print` ships first, and this keeps a document that needs it
  from losing it here. It applies at any depth, to `validate`, `toBytes`, `write`
  and `layout`.
- **Reading a file with section breaks now says what it flattened.** `read()` has
  always taken one page setup from such a file, the last section's, silently. It
  now adds `unrepresented: [{where: "/page", kind: "layout-not-preserved", count}]`,
  `count` being the section breaks lost, and `describe()` gains a line for it. Not
  breaking: blocks, `page` and everything else read as before, and the key appears
  only on such a file. A later release reads the sections themselves.

### Fixed

- **`validateAndRepair` no longer deletes what it was about to refuse.** Repair
  rewrote every break to `{"type": "pageBreak"}`, so with any unrelated repair in
  the document, a break carrying `page` or a near-miss key would have come back
  `ok: true` with the key gone. Those keys now stay, and the result is `ok: false`.
  Other extra keys on a break are still stripped by repair, as before.

## [0.17.0] - 2026-11-01

**What you must do: nothing.** One new method; nothing existing changed. It is
PHP-first: `last-word-js` and `last-word-py` do not have `layout()` yet.

### Added

- **`Agent::layout($doc, $options = [])`: the page count, computed without a
  browser** (MOIC, 2026-11-01). Returns `pages` (int), `pageStarts` (per page,
  the index of the top-level block it starts with; `null` for an empty page),
  `pageList` (per page: its blocks, whether the first continues from the page
  before, its footnote numbers, body `used` / `capacity` in points and `fill`
  0..1), `page` (size, width, height) and `font`, plus `approximate`: what it
  could only estimate (a font other than Calibri, code, a character Carlito
  lacks, a date or time field). An empty `approximate` means exact.
  - It is the pagination `@particle-academy/last-word-ui` 0.3.0 draws, which
    renders Calibri and unspecified text in a bundled Carlito. The same rules,
    in PHP: greedy line breaking on Carlito's advance widths per run (size,
    bold, italic, letter spacing), the viewer's spacing defaults, headings with
    keep-with-next, list indents, quotes, tables (column weights, collapsed
    borders, row heights, the header row repeated, rows never split),
    footnotes taking room on their mark's page, widow and orphan control, and
    the page model: size, orientation, margins, header and footer distances,
    and one body height per page class (page 1, even, odd) from the bands each
    draws.
  - Takes the same options as `toBytes()`. With a `template`, the document is
    laid out as it reads back after writing (that is what the viewer is
    given), so a letterhead taken with `templateParts` and
    `templateFirstPageOnly` costs page 1 its real height. Taking the
    template's `styles` can bring its font (the test letterhead brings
    Garamond); `approximate` then says so.
  - Agreement: on the shared fixtures
    (`tests/fixtures/layout/viewer-agreement.json`: MOIC's ~570-word
    letterhead memo, on a band and on a template, its ~860-word letter,
    footnotes, a 70-row table, keep-with-next, first/even bands, edge cases),
    the page count and every page start equal the viewer's in Chromium, and so
    does every measured input: each block height, line breakpoint, table row,
    band and footnote height, and footnote mark position.
  - `resources/layout/carlito.json`: Carlito 1.104's advance widths (every BMP
    codepoint it maps, four styles), derived from the font files (the sha256 of
    each is in its `provenance`), and the line-box heights measured in
    Chromium. `LastWord\Layout\PageLayout::measure()` returns the measured
    input, for tracing a disagreement block by block.
- Agent guide: measure the length with `layout()` rather than a word count
  (the guide's bytes and hash changed; copy them into the Node and Python
  packages at their next release). New sha256:
  `cb47bdfa50116a89f5b046f044728abbee2b0455dd5dd6ecb16ef15600db1e72`.

## [0.16.0] - 2026-11-01

**What you must do: nothing, unless you want a first-page letterhead, first or
even bands, the new header/footer fields or `meta.author`.** With
`templateFirstPageOnly` absent or `false`, no variant band, no `meta` and none of
the new tokens, every document writes exactly what 0.15.0 wrote, part for part
(pinned by part digests taken from released 0.15.0). Two read-side changes and
one write-side change can touch an existing document; see Changed. Release
order: **`fancy-conformance` 0.41.0 first** (this package's dev dependency is
pinned to it exactly; nothing at runtime depends on it).

### Added

- **The letterhead on the first page only: `templateFirstPageOnly`** (MOIC,
  2026-11-01). A write option beside `templateParts`, boolean, default `false`.
  When `true`, the template header and footer that `templateParts` takes become
  Word's FIRST-page header and footer (`w:titlePg` on): the template's own
  first-page part when its `w:titlePg` is on and it has one, otherwise its
  default part; never its even part. Later pages get the document's own
  `page.header` / `page.footer`, or nothing. A document `page.firstHeader` /
  `page.firstFooter` still wins over the template's for that kind. The carried
  part is `word/{kind}4.xml` (`rIdTpl{Kind}4`). A non-boolean value throws
  `TemplateException`; ignored without a `template`.
- **First-page and even-page bands: `page.firstHeader`, `page.firstFooter`,
  `page.evenHeader`, `page.evenFooter`**, each the same shape as `page.header`
  (a one-line band or a `{blocks}` band). `page.header` stays "every page"; with
  a `firstHeader` it is every page but the first, with an `evenHeader` the odd
  pages. A kind with no variant shows its default on those pages too. An empty
  variant (`{"blocks": []}`) blanks that page when the kind has a default band.
  Written as Word's `first` / `even` header references (`w:titlePg`,
  `w:evenAndOddHeaders` in settings), parts numbered by slot: `{kind}1.xml`
  default (unchanged), `{kind}2.xml` first, `{kind}3.xml` even. `read()` returns
  them from any producer, so a first-page-only letterhead reads as
  `firstHeader` with no `header`. Footnotes stay refused in every band.
- **Field tokens in header and footer text**: `{section}`, `{sectionpages}`,
  `{author}`, `{title}`, `{filename}`, `{date}`, `{time}`, and
  `{date:FORMAT}` / `{time:FORMAT}` with a Word date-time picture (one or more
  characters, none of `{`, `}`, `"` or a backslash), beside `{page}` /
  `{pages}`. Each is a live complex field, written by the same code `{page}`
  already used. The cached result is deterministic: `1` for page and section
  numbers; `meta.author` and the `title` for AUTHOR and TITLE; nothing for DATE,
  TIME and FILENAME (no clock: the same document still writes the same bytes).
  Without a picture, DATE and TIME show in the reader's locale. Anything else in
  braces stays literal, and every token stays literal in the body. `read()`
  returns any producer's field as its token. `Schema::FIELD_TOKEN`,
  `Schema::splitFieldTokens()` and `Schema::fieldTokenOf()` are the grammar.
- **`meta.author`**: `docProps/core.xml` `dc:creator`, written after
  `dc:title` and read back. The title stays the top-level `title`; there is no
  `meta.title` (validation refuses it and `validateAndRepair` moves it to
  `title`), so `dc:title` has one slot.
- `Schema::PAGE_BANDS` / `Schema::PAGE_BAND_SLOTS`; `describe()` lists blocks
  in every band.
- Agent guide: the first-page band, the letterhead option and the field tokens
  (the guide's bytes and hash changed; the Node and Python packages carry the
  same bytes). New sha256:
  `6d70d774cf630c0c40813d70ddd00191cc8a0b57a2cd3c603cae54f64a9501fa`.

### Changed

- **`read()` of a document with `w:titlePg` on, or `w:evenAndOddHeaders` on,
  now returns `firstHeader` / `firstFooter` / `evenHeader` / `evenFooter`.**
  Before, only the default band was read and the first/even ones were lost.
  Consumer action: none to keep working; a document read and written back now
  keeps its different first page. If you compared `page` keys exactly, expect
  the new ones.
- **`read()` of a SECTIONPAGES field now returns `{sectionpages}`** (it was
  `{pages}`). Consumer action: none; in a one-section document both show the
  same number, and writing `{sectionpages}` back writes SECTIONPAGES again.
- **A header or footer whose text already contained one of the new tokens
  literally** (say `{date}`) now writes a live field there. Consumer action:
  only if you meant the braces literally; write `{Date}` or another
  non-token spelling.

### Fixed

- A field that is not a token, in a one-line header or footer from another
  producer (a STYLEREF, say), lost its cached result on read; it now keeps it
  as text, as a `{blocks}` band already did.

### Notes

- `particle-academy/fancy-conformance` (require-dev) is pinned exactly at
  `0.41.0`: `last-word/docx-constructs` rows 0054-0079 pin the letterhead
  option, the band variants, the field tokens and `meta` for all three engines,
  with new functions `bandParts`, `bandFields` and `coreProps` and a row input
  of `{doc, template?, options?}` (the template is a document model).
- LibreOffice 26 (build 8221e31) renders a `templateFirstPageOnly` letterhead on page one only
  (the logo drawn on page 1 and on no other) with the document's own header
  after it, and computes every new field on load.

### PARITY

- The Node (`@particle-academy/last-word`) and Python ports have none of this
  yet. They mirror it by bumping to fancy-conformance 0.41.0, passing rows
  0054-0079 (harness: pass `input`, write `input.template` and pass it with
  `input.options`), implementing the three extractors, and copying the agent
  guide bytes and hash. `doc-model/shared` 0001 and 0002 record `meta` and the
  four variants as last-word-only.

## [0.15.0] - 2026-11-01

**What you must do: nothing, unless you want footnotes or the header/footer
distances.** No existing document writes or reads differently: a document
without a footnote is byte-identical, and `read()` output is unchanged for every
file that has no footnotes and default header/footer distances. Release order:
**`fancy-conformance` 0.40.0 first** (this package's dev dependency is pinned to
it exactly; nothing at runtime depends on it).

### Added

- **Footnotes** (MOIC, 2026-11-01). A footnote is a RUN placed where the mark
  goes: `{"text": "", "footnote": {"blocks": [...]}}`, its blocks the body's
  vocabulary less `chart` and `pageBreak`. Word numbers the marks in document
  order; the model carries no number. Allowed in headings, paragraphs, list
  items, table cells and quotes; refused in a header or footer and inside
  another footnote (Word has neither). `validateAndRepair` sets a missing `text`
  to `""`, moves text typed on the mark into a run before it, wraps a string or a
  bare list of blocks, and drops a misplaced footnote with a note.
  - `toBytes` writes `word/footnotes.xml` with the separator (`w:id` -1) and
    continuation separator (0) Word requires, `w:footnotePr` naming them in
    `settings.xml`, a `FootnoteReference`-styled `w:footnoteReference` run, the
    relationship and content type, the `FootnoteText` / `FootnoteReference`
    styles (only when a footnote exists; a template's own definitions win), and
    `word/_rels/footnotes.xml.rels` for a footnote's links and images.
    LibreOffice renders the notes at the foot of the page, under the separator
    rule and above the footer, and its own `.docx` export of the file reads back
    with every footnote.
  - `read()` returns the same run for a `.docx` footnote from any producer: any
    ids, Word's separators and continuation notices skipped, the space after a
    footnote's own number stripped, a run holding text and a reference split in
    two. A reference whose footnote is missing reads as nothing. A footnotes part
    declaring a DOCTYPE is not read.
  - Agent guide: one idiom and example (the guide's bytes and hash changed; the
    Node and Python packages carry the same bytes).
- **Header and footer distances: `page.margins.header` / `page.margins.footer`**,
  points from the page edge to the header and to the footer (`w:pgMar` `header` /
  `footer`; 36 by default). Written and read symmetrically, and they override a
  template's distances field by field, as the four sides already did.
- **`Schema::pageMargins($doc)`**: all four margins and both distances, defaults
  filled in, for a paged viewer. `Schema::PAGE_MARGIN_DEFAULT` (72) and
  `Schema::PAGE_BAND_DISTANCE_DEFAULT` (36) name the defaults.

### Notes

- **The margin rule is unchanged, and now documented.** `read()` omits any margin
  equal to its default (72pt a side, now also 36pt a distance) and omits `page`
  when nothing differs, so "no bottom margin" in a read document means one inch,
  not none. Emitting every side would have changed the read output of every
  existing document and fixture. **Consumer action for a viewer:** resolve with
  `Schema::pageMargins()` (or the same defaults in your language) instead of
  treating an absent margin as zero.
- **Not covered yet:** the `.doc`, `.odt` and `.rtf` readers still skip footnotes
  (as they always have; this release did not change them). Markdown, HTML,
  plain-text and portable export do not carry footnotes: the mark vanishes there
  and the footnote's text is not exported.
- `particle-academy/fancy-conformance` (require-dev) is pinned exactly at `0.40.0`:
  `last-word/docx-constructs` rows 0045-0053 pin the footnote and page-geometry
  contract for all three engines, and `doc-model/shared` 0006 records `footnote`
  as a last-word-only run property.

### PARITY

- The Node (`@particle-academy/last-word`) and Python ports have none of this
  yet. They mirror it by bumping to fancy-conformance 0.40.0 and passing rows
  0045-0053 (with the new `footnotesPart` extractor) and copying the agent guide
  bytes and hash.

## [0.14.0] - 2026-10-29

### Added

- **Headers and footers that hold blocks, so a read letterhead keeps its logo**
  (last-word#6). `page.header` / `page.footer` may now be `{blocks: [...]}` in the body's
  own block vocabulary (less `chart` and `pageBreak`, at any depth, and `portable`)
  instead of the one-line `{left, center, right, size, color}` band. The two forms never
  mix: a band with both is a validation error. In a blocks band, `{page}` and `{pages}` in
  run text are live page fields, as in a band.
  - **`read()` output changes only for headers and footers it could not hold before.**
    A header or footer that is one paragraph of text and nothing else reads exactly as it
    did. One that held a picture, several paragraphs, a table or a content control (Word's
    own "Page X of Y" footer is one) now comes back as `{blocks}`: the logo as an image
    block with a `data:` URL like a body image, PAGE / NUMPAGES as `{page}` / `{pages}`.
    Those documents were the lossy ones: their logo or extra lines were reported under
    `unrepresented` and dropped. `unrepresented` now lists only what blocks cannot hold
    either (VML pictures, embedded objects, GIF / EMF and other non-PNG/JPEG images,
    linked or oversized images, text boxes as `image`; charts as `chart`).
    **Consumer action:** if you read `page.header.left` (or `center` / `right`), also
    accept `page.header.blocks`; a viewer draws it like any other blocks. If you write a
    read document back onto its own original with `templateParts`, keep dropping
    `page.header` / `page.footer` first, as before. Without a template, leave them in:
    the logo and address now write back on their own.
  - `toBytes` writes a blocks band through the body's block renderer into `header1.xml` /
    `footer1.xml`, wrapped in a `lastword:band` content control (so a one-paragraph blocks
    band reads back as blocks), with the part's own relationships file. Media names, drawing
    ids and relationship ids cannot collide with the body's or with a `templateParts`
    letterhead's, and the document's own band still replaces the template's.
  - Hardening equal to 0.13.0's letterhead media, on both paths: a header or footer image
    must be PNG or JPEG by its leading bytes and its declared type, at most 16 MiB each and
    32 MiB across the header and footer. On read, a linked picture is never read (nothing

## 0.6.0 — 2026-09-14

### Added

- **`Agent::diff()`, `Agent::reduce()`, `Agent::opSchema()` and `Agent::equivalent()`:
  a document's versions stored as ops** (last-word#2). A version history cannot

## 0.5.0 — 2026-09-13

### Added

- **`Agent::read()` reads legacy Word `.doc` (Word 97-2003)** (last-word#1).
  0.4 refused it by name, which was honest and left a host with nothing to give
  a model. The compound-file container (MS-CFB) and the Word binary format
  (MS-DOC) are read by code in this package; there is no new dependency.

  What comes through: paragraph text from every piece of the piece table
  (fast-saved files included, 8-bit and UTF-16 pieces), headings by the style's
  built-in identifier (so "Überschrift 1" is still a heading), directly applied
  bold / italic / underline / strike, hyperlinks from `HYPERLINK` fields (other
  fields keep their displayed result), bulleted and numbered lists with nesting,
  tables with header rows, and page breaks.

  What does not: formatting inherited from a style, fonts, sizes and colours,
  images and embedded objects, text boxes, headers, footers, footnotes and
  comments, merged cells, and the document title.

  Word 6/95 files and encrypted files are refused by name
  (`UnsupportedFormatException`, `format()` `doc`). A compound file that is not
  a Word document is named too: `xls`, `ppt`, `msg`, or `cfb`.

- **The same document now reads the same in all four formats.** A document
  written by this package and converted by LibreOffice to `.doc`, `.odt` and
  `.rtf` reads back **identically** to the `.docx` from the `.doc` and the
  `.odt`, and identically from the `.rtf` except for a header-row flag that
  file does not carry. `LegacyFormatsTest` asserts exactly that on committed
  fixtures (`tests/fixtures/formats/`, with a README saying how they were made).

- **Office files that are not word-processing documents are named.** An
  `.xlsx`, `.pptx`, `.ods` or `.odp` raises `UnsupportedFormatException` with
  that format, rather than "not a document".

### Changed

- **The ODT reader keeps far more of the document.** Bold, italic, underline
  and strike from automatic styles (where ODF keeps direct formatting),
  hyperlinks, lists with nesting and numbered/bulleted from their list style,
  tables with header rows and merged cells, `text:s` / `text:tab` /
  `text:line-break`, page breaks, and the title from `meta.xml`. 0.4 returned
  headings and paragraphs as plain text.

  The shape changes with it: a list item that 0.4 returned as a top-level
  paragraph is now an item of a `list` block, and a table cell's paragraph is
  inside a `table` block. A caller that walks blocks by `type`, as it already
  must for a `.docx`, needs no change; one that only read top-level paragraphs
  of an `.odt` will now find that text inside lists and tables.

- **The RTF reader is a real tokenizer with group-scoped state.** It reads
  headings by style name or outline level, direct bold / italic / underline /
  strike, `HYPERLINK` fields, lists from the list table, tables (header rows
  where `\trhdr` marks them), `\uN` with `\ucN` fallback skipping and surrogate
  pairs, `\'hh` in the document's code page (`\ansicpg`: 874 and 1250-1258
  decoded; 932/936/949/950 double-byte characters become one U+FFFD each), line
  breaks, tabs, page breaks and the title.

  **BREAKING, for RTF only:** 0.4 turned any bold-led paragraph into a level-1
  heading. That was a guess, and it made emphasis into structure. A bold
  paragraph is now a paragraph with a bold run; a heading is a paragraph whose
  style or outline level says so. If you relied on the guess, look for a
  paragraph whose runs are all bold.

- **Bytes that are no document raise `UnsupportedFormatException`** (format
  `unknown`) instead of a bare `InvalidArgumentException`. It extends
  `InvalidArgumentException`, so a `catch` for that still catches it; do
  nothing unless you compared the class exactly.

- **A damaged file raises `RuntimeException`, and an unsupported format raises
  `UnsupportedFormatException`.** "This file is broken" and "save it as .docx"
  send a person to do different things. A `.doc` signature with nothing valid
  behind it was an unsupported format in 0.4 and is a damaged file now.

### Security

- **Legacy readers treat an upload as hostile.** Every compound-file offset is
  bounds-checked; sector chains, the DIFAT chain and the directory tree are
  followed at most once per node, so a loop fails instead of spinning; a stream
  over 256 MB, or an allocation table naming more sectors than the file holds,
  is refused; the Word piece table must run forwards, so no byte range is read
  twice; an ODT part carrying a DOCTYPE is refused before parsing, parts over
  64 MB are refused, element nesting past 257 is refused (libxml's own limit,
  now pinned by a test so the Node and Python parsers refuse at the same depth),
  and repeated rows and columns are capped (1,000 per repeat, 100,000 cells in
  total); RTF group nesting is capped at 10,000 and `\bin` data
  is skipped by its length. Each guard has a test on a hand-built file
  (`tests/Support/LegacyFiles.php`).

  at once — all eight run properties in a single paragraph, styled headings, a
  repeating table header, resolved list numbering, A4 landscape geometry, a
  document default font — and asserts the unzipped OOXML rather than that a file
  appeared.

  The suites beside it prove each feature works ON ITS OWN. That is a different
  question from whether they compose, and a dropped feature is invisible: Word
  shows no error and the document is merely plain. Nobody files a bug against a
  report that looks boring; they conclude the library is boring.

  It found no defects here, which is the result worth recording. It includes a
  control that fails if the assertions could pass on an unformatted document,
  and it pins two decisions that read like gaps: `highlight` renders as `<w:shd>`
  rather than `<w:highlight>` (which takes sixteen named colours and could not
  carry a `#RRGGBB` schema), and `page.margins` are in POINTS.

## 0.4.0 — 2026-09-10

### Added

- **`Agent::read()` now reads ODT and RTF, and NAMES a legacy `.doc` instead of
  failing obscurely** (last-word#1).

  A consumer removed `phpoffice/phpword` and made this package the only docx
  path in their app. PhpWord's `IOFactory` sniffed `.doc`, `.odt` and `.rtf`
  alongside `.docx`; dropping it dropped those three.

  **The failure was silent, which is the part that mattered.** Those arrive as
  user uploads that an agent then analyses: the file stored fine and contributed
  no text. Nothing raised, nothing logged, and an agent answered questions about
  a document nobody had read.

- **`UnsupportedFormatException`**, distinct from `InvalidArgumentException`.
  "This file is damaged" and "this is a format we do not read, save it as
  .docx" lead a person to different actions, so they cannot share a class. It
  carries `format()` so a host can branch without grepping a message — messages
  are for people, and a host that parses one breaks when the wording improves.

  A legacy `.doc` is detected and refused by name. Binary Word 97-2003 parsing
  is a separate and much larger job; refusing it clearly is the honest answer
  today, and it is what lets a host say "re-save it as .docx".

### Fixed

- **A path is now sniffed, not assumed to be docx.** `read()` used to treat any
  existing path as docx bytes — reading the file and handing it to `DocxReader`
  without checking the signature — so a `.doc` on disk failed *inside the zip
  reader* and the error named a broken archive rather than the real problem.

### Reading, honestly scoped

  ODT keeps structure: `text:h` becomes a heading with its level, not a
  paragraph. The consumer left another library precisely because it flattened
  nested lists and stripped emphasis, and text that survives with its shape lost
  is a worse input for a model than text that fails loudly.

  RTF extraction takes paragraphs and bold-led headings. RTF carries much more —
  tables, embedded objects, styles — and this does not claim them. Stated here
  rather than discovered.

  Both return **the same document shape as `DocxReader`**, so a caller that
  already handles our documents needs no second code path per input format. The
  moment it does, the two paths drift and only one gets the next fix.

### Added

- **A rich-layout surface, so a business one-pager is expressible.** The model
  was far narrower than the XML this engine already emitted: font size, font
  family, small caps, letter spacing, per-cell shading, borders, padding,
  vertical alignment and both merge directions were produced from hardcoded
  blocks or from `styles.xml` and were **unreachable from the model**. An agent
  could emit `size`, `colSpan` or `shading`, the validator returned no errors,
  and every one of them was silently dropped.

  | where | new keys |
  |---|---|
  | run | `size` (points, half-points exact) · `font` · `smallCaps` · `letterSpacing` (points, may be negative) |
  | paragraph, **heading** and list item | `spaceBefore` · `spaceAfter` · `lineHeight` · `indentLeft` · `indentRight` · `keepNext` · `shading` · `borders` · `align` (on headings too) |
  | table | `widths` (relative column weights) · `width` (% of the text column) · `align` · `borders` (incl. `insideH` / `insideV`) · `cellPadding` |
  | cell | `shading` · `borders` · `padding` · `valign` · `colSpan` · `rowSpan` |
  | document | `page` (`size`, `orientation`, `margins`) · `defaultFont` · `defaultSize` |

  Every key is validated, every key round-trips through the reader, and every
  key appears in `jsonSchema()` so an agent registering the tool is told it
  exists.

- **A heading is now a paragraph.** It takes the same properties, so a section
  label that needs spacing or alignment no longer has to be a bold paragraph
  impersonating a heading — and therefore appearing in no navigation pane and
  no table of contents.

- **Both merge directions**, written HTML-style: a `rowSpan` cell appears ONCE
  and the rows it covers list only their own remaining cells. The writer
  synthesises the `w:vMerge` continuations OOXML requires and the reader folds
  them back, so the model that comes out is the model that went in.

- **The table grid is computed from the section.** All three engines carried
  `9360` twips as a literal, so a document that narrowed its margins got a
  table that no longer matched its own page — too narrow, and silently so.

- **`last-word/docx-constructs` in `fancy-conformance`** — 44 shared rows
  pinning which construct emits which XML, in which order, and what the reader
  gives back. The rows are not transcribed into this repo: all three engines
  assert the same file, so a mapping that drifts in one fails there rather than
  quietly becoming that engine's behaviour.

### Fixed

- **Adjacent tables no longer merge into one in Word.** OOXML merges two
  `<w:tbl>` elements that touch, imposing the first table's column grid on the
  second. A stat band followed by a callout became a single two-row table.
- **A run's properties can no longer be lost to run-merging.** Adjacent runs
  are merged when their formatting matches, and the comparison listed only the
  properties that existed when it was written — so two differently-sized runs
  merged into one and took the first one's size.

- **`fancy-conformance ^0.7.0` is a new dev dependency**, and it is not on
  Packagist yet — the fixture package has to be released before this one can
  install. `composer.lock` is deliberately NOT updated here for that reason;
  regenerate it once the fixture release lands.

### Changed

- **Table properties are now written inline, not taken from a named style.**
  A named table style cannot vary per table instance, so per-table borders
  forced this. Also reconciled with it: header cells are one grey in all three
  engines, and header bold is one mechanism.

- **Document defaults name an East Asian font.** Without it Word picks its own
  face for CJK runs, which is exactly the text a mixed-script document
  contains.

  **What you must do: nothing.** No existing key changed meaning, nothing was
  removed and nothing was renamed. A document written before this release
  produces the same page. The visible differences are confined to tables, are
  small, and are listed above so a pixel comparison against an old build is not
  a surprise.

### Notes

- **A `header: true` row is not a round-trip fixpoint, and now says so.** The
  writer bolds the row's runs and the reader honestly reports the bold it
  finds, so the model that comes out is not the model that went in. The
  alternatives were to stop bolding header rows (changing every existing
  consumer's output) or to have the reader strip bold from header rows
  (discarding bold an author really asked for). Pinned as case `0042` rather
  than left as a surprise.

- **Release order: `fancy-conformance` first.** The shared table is version
  `0.7.0`, which is not on a registry yet, so this package's dev dependency
  cannot resolve and its lockfile cannot be regenerated until that release
  lands. Nothing about the runtime surface depends on it — only the test that
  asserts the shared rows.

- **What DOCX cannot do, so nobody chases it:** table corners are always
  square (there is no border radius in WordprocessingML), a background cannot
  bleed past the page margin without an anchored drawing, and naming a font is
  not shipping one — a reader without it substitutes. None of the three is
  worked around here; a layout that needs them needs a different format.

## 0.3.0 — 2026-08-07

### Changed

- **BREAKING — PHP 8.2 is no longer supported.** `require.php` moves from `^8.2` to `^8.4`.

  **What you must do:** on PHP 8.4 or newer, nothing. On 8.2, either upgrade PHP first or stay on the previous release — it keeps working and is unaffected by this.

- CI now tests PHP 8.4 only, instead of a matrix spanning versions this package no longer claims to support. A matrix that tests what the manifest forbids is worse than none — it reports green for a combination nobody can install.

### Why

These are the kit 0.5 platform floors. The suite was split across PHP 8.2 and 8.3 with the framework spanning 11–13, so no package could rely on anything newer than its weakest sibling. Every PHP package in the kit takes the same floors at once, so a consumer never has to resolve a mix.

Pre-1.0, so this lands in a MINOR. **No API changed, nothing was removed, nothing was renamed** — only what the package requires.
